## 二、逐层拆解（带实锚）

### 2.1 桌面派工台（`C:\Users\74153\Desktop\AFK派工台-启停.cmd`）

性质：**纯开关台**。七个菜单项没有一个自己长驻跑派工——[1] 只做三件事：启用计划任务、立即触发一轮、手动投影一次飞书；[2] 停止=停任务+禁用+按**进程名单正则**清场（`pi_runner|approval_poll|window_card_sync|afk_cron|queue_watcher`，W-116/拍板#168 补入 queue_watcher——此前漏加导致关引擎后快车道 watcher 残留）。

### 2.2 计划任务「AFK厂务派工」（心跳源）

schtasks 实查（2026-10-26）：

| 项 | 值 |
|---|---|
| Task To Run | `wscript.exe "…\91-脚本\afk_cron_hidden.vbs"` |
| 循环 | 每 30 分钟（Repeat: 0:30） |
| 开机自启 | 可选 AtLogOn 触发器，由 `afk_autostart.ps1` toggle 加/摘（afk_autostart.ps1 L4-20） |
| Logon Mode | Interactive only（弹出的施工子窗可见的前提） |
| 超时熔断 | Stop Task If Runs 72:00:00 |

`afk_cron_hidden.vbs` 只有一行：`WScript.Shell.Run …afk_cron.cmd, 0, False`——**窗口参数 0=隐藏**，这就是「后台无人值守但 pi 施工子窗仍可见」的分界：cron 宿主藏起来，施工窗由 spawn_window 单独拉可见窗。

### 2.3 `afk_cron.cmd` 六步（每轮心跳做七件事）

顺序：approval_poll → detached 拉起 queue_watcher（W-116/A2·不阻塞宿主）→ **window_card_sync（投影①）** → wip_scan --check-feishu（落差核查）→ 读 spawn 形态状态件（白名单闸）→ **pi_runner --auto --loop --max-hours 4（派工主循环）** → **window_card_sync（投影②）**。全部输出追加进 `91-脚本/.dispatch-cron.log`。

### 2.4 快车道 queue_watcher（拍板#130·借鉴 VCP taskScheduler「过期即执行」）

目的：**消灭 30 分钟 cron 边界等待**——主对话窗五步派工链把票落成「待实施(已批)」后，watcher 立刻看到、立刻派工（queue_watcher.mjs 头注 L1-10；`hasClaimableRow` 判定口径=第 5 列严格等于「待实施(已批)」）。防抖 30s 防队列连写风暴；单飞锁 `os.tmpdir()/queue-watcher.pid`；watch 挂了如实 exit 1，由 cron 每轮 detached 再拉（死亡自愈靠兜底不靠装绿）。

## 三、飞书状态怎么触发、怎么写（业主第二问专答）

### 3.1 一句话总纲

**飞书「AFK窗卡台」没有自己的触发器，它是本地窗队列的投影**：`90-过程/窗队列.md` 是唯一事实源，`window_card_sync.mjs`（机械设备零 LLM）把行状态单向推进飞书 multi-dimensional table（base `VQ4IbmbWtaxfRGsd1rIc241InIf`），**永不反向**（window_card_sync.mjs 头注 L2-3）。

### 3.2 四道触发（全部殊途同归到同一个 `syncQueue()`）

| 道 | 触发时机 | 挂点 |
|---|---|---|
| ①cron 周期投影×2 | 计划任务每 30 分钟，afk_cron.cmd 第③步（派工前）+第⑦步（派工后）各一次 | afk_cron.cmd |
| ②事件道（秒级·主道） | `window_card_sync.mjs --watch` 常驻：fs.watch 队列所在目录 → 防抖 2s（30s 帽防饿死）→ 秒级投影；30min 进程内定时保底并行；watch 失效→WARN 自动退定时道，每轮定时尝试重挂自愈 | `startWatchLoop`（window_card_sync.mjs，DEBOUNCE_MS=2_000/MAX_WAIT_MS=30_000/SYNC_INTERVAL_MS=30min） |
| ③watch 转正（事件道的拉起方） | 每轮 `pi_runner --auto` 启动段 `armSyncWatch()`：锁 `os.tmpdir()/afk-sync-watch.pid` 单飞，活着不重复拉，死了 detached 重拉（跨周期常驻·崩了下轮 cron 兼容底复活） | pi_runner.mjs L725-741 |
| ④手动道 | 派工台 [1] 启动派工第 3 步直接 `node window_card_sync.mjs`（全量对账一次·幂等） | 桌面 cmd :start 段 |

也就是说：**行一被写（落票/领单翻▶/收口翻✅🔁），2 秒内事件道就投影；事件道坏了退 30 分钟定时道；cron 周期再兜两道底**——观察期多道并存（拍板#89③ 先例），不装绿。

## 三（续）、飞书状态写入流水·反向核对·时序体感（§三拆节下半·业主第二问专答）

### 3.3 写入流水（`syncQueueOnce`，全机械零 LLM）

1. **单飞互斥**（W-054/拍板#107）：取锁 `.window-card-sync.lock`——锁在+持 PID 存活=拒启记因退出（治「手动 sync 与计划任务并发→record-list 互查不到→双建」实证根因）；死锁=摘陈锁接管；finally 只摘自己的锁。
2. **读事实源**：parseRows 解析窗队列（解析器单源在 window-card.mjs `parseWindowQueue`，W-048/拍板#103 切换）；「0 行但文件非空」=疑写中半截，本轮跳投不装绿。
3. **建映射**：三表各跑 `lark-cli base +record-list --format ndjson`，防御式提取 (窗ID→record_id)（拍板#74：ndjson 修复前 json 矩阵无 record_id 是「每轮翻倍新建」的根因之二）。
4. **分流**（W-049/拍板#104）：`routeTableOf` 按大业务分表——App 三类→T1a（`tblo3LUJqHwZ9Lgq`）、引擎两类→T1b（`tblfAqRyefnmMuz2`）、空/五类外→T1b 缺省+记因；**每行双写**（分流表+旧表 `tblfvvXffnFX1kVg` 观察期）。
5. **组 payload**（`cardPayload`）：窗ID/主题/型/拍板号/下一棒锚/产物锚/更新/窗PID（读 `afk-window-pids.json` 带「存活/已退」判定）/前置/领地；**两道白名单闸**——状态非七态词=状态键跳投+`[WARN]` 告警（W-074/拍板#124，治收口文案灌状态格→飞书票面永不更新）；大业务五类外=跳投、空=缺省「引擎优化」。
6. **批写**（`runBatchWrite`）：有 record_id→`lark-cli base +record-batch-update`，无→`+record-batch-create`；≤25 行/批（拍板#97 从 200 收紧）；`--json @临时文件` 绕引号、`windowsHide` 治闪；**失败 3s 后自动重试一次**（W-026，治并发撞车瞬态），再败→**降级逐行隔离续跑**（拍板#130，坏行不拖累好行），坏行明细落 `91-脚本/sync-errors/*.json`（含 log_id·只留 20 份）。
7. **幂等零翻倍**：映射命中=更新、不命中=新建，同表连跑两遍=「更新 N·新建 0」（selftest 案8 断言在案）。

### 3.4 反向核对道（只读·不写）

`wip_scan.py --check-feishu`（afk_cron 每轮第④步）：lark-cli record-list **只读**拉飞书状态列，与本地✅行比对——飞书非✅/缺行 → `WARN 落差: <窗ID> …`（告警级不拦车·拍板#120 题7 乙）。这是唯一「看飞书」的道，且只读不写，方向纪律零例外。

### 3.5 时序体感（一行票的一生）

| 时刻 | 动作 | 飞书可见延迟 |
|---|---|---|
| 拍板落票 → 待实施(已批) | 事件道 watch 到写盘 | **约 2 秒** |
| pi_runner 领单 → ▶施工中 | 同上 + cron 第⑦步兜底 | 约 2 秒（事件道坏时最迟 30 分钟） |
| 施工窗退出 → ✅/🔁 | 钩子直写行 → 事件道 | 约 2 秒 |
| 票面落差（本地✅飞书没跟上） | wip_scan 只读告警 | 下一轮 cron（≤30 分钟）出 WARN |

**保险丝设计**：事件道（快）坏了不装绿——WARN 入账自动退 30 分钟定时道，每轮定时尝试重挂自愈；cron 两道投影永远在跑（最坏情况延迟一轮心跳）；单飞锁防「手动+定时并发双建」；所以飞书状态可能**晚到，但不会错方向**——错方向只会被 wip_scan 的落差告警点名。
