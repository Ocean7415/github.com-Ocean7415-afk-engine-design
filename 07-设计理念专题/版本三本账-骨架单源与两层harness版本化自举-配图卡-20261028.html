卡6 · 骨架 S1.x 详解：一份图纸三件套 它现在还不是实体类 · 卡1 深化 · v2 增补

术语白话对照：模板方法模式＝父类定流程（焊死不许改）、子类填内容的面向对象手法｜钩子方法＝基类里留空的「填空题」，每个实例填自己的做法｜spawn 子进程复用＝第二层要跑同一条流水线时，不是引用同一段代码，而是另开一个独立进程去跑——隔离性好但代码层面是两套｜Pull Up（上提）＝把多处重复的代码上提为一份共享母版的重构手法。
口述：把骨架想成全厂唯一一张发动机图纸。图纸上画三样东西。第一样是流水线的工序顺序（模板方法基类）：夜车开工必须按「入夜门禁六硬项→导入拆单→探针编译装备→施工→质量门→切片验收→报告」的顺序走，一步不改。这段顺序今天真实存在，但它是写在一个函数体里的——像一道菜谱抄在一张纸上，谁想做这道菜就整页抄一遍（第二层就是整进程抄：开个子进程跑同一条流水线），而不是照着「菜谱母版」各做各的。第二样是标准零件库（机械件包）：五十八个两层共用的零件——记流水账的账本、防偷改考题的判卷守卫三卫、大模型档位旋钮、防提示注入的变量盒封套等。注意它们的形态：绝大多数是纯函数和常量，只有账本等少数是真类——「零件包」是零件的集合，不是面向对象的类库。第三样是交货单格式（交接契约）：班与班之间交货凭机器可查的凭据，凭据格式已在码里，而「接口契约台」（逐项对账的机器面）还挂在候拍窗 W-152 名下没落码。
所以回答「骨架是不是一个实体对象类」：现在不是——三件里没有一件以「类」为中心形态存在，站序是函数、零件是模块、契约是类型定义。步④拍板后才是——把函数体里的焊死站序上提为一个抽象基类的模板方法，各站留填空：第一层继承它填「造客人 APP 的做法」，第二层继承它填「管团队的做法」。届时的样子大致是：基类里 run() 流程焊死不许改，preflight/build/verify 等站留成填空钩子，两个实例类各自继承填空。为什么要费这个劲？一是两层同构现在全靠文档互相指认，代码层各写各的，久了必漂移——基类化后同构等于继承，改一处两处自动跟；二是版本记账需要它——「骨架版本 S1.x」要成为一个边界清晰的实体才钉得进夜车入口的钉版文件；三是自举需要它——造新版的车和被造的零件共享同一张图纸，账才对得上。设计件把它排 P2「提效不设卡」：因为进程边界已提供隔离复用，基类化是省力活不是保命活。
// 步④基类化后的形态示意（非实码·真实设计以步④拍板件为准）
abstract class NightShiftSkeleton {        // ← 骨架 S1.x 的实体形态
  final async run(pkg): ExitCode {         // 模板方法：站序焊死，子类不许改流程
    await this.preflight();                // 段0 入夜门禁
    const plan = this.importAndSplit(pkg); // 段1 导入+拆单
    await this.build(plan);                // 段2 施工
    await this.verify();                   // 段3 验收
    return this.report();                  // 收尾报告
  }
  protected abstract preflight(): void;    // 站实现＝填空（钩子方法）
  protected abstract build(plan): void;
}
class TeamL1 extends NightShiftSkeleton { /* 造客人 APP 的填空：岗卡+系统提示词常量 */ }
class ManagerL2 extends NightShiftSkeleton { /* 管团队的填空：六闸+维修环+派工 */ }
