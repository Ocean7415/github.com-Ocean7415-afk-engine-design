# 设计理念 · 为什么走派工单（L2 pi 窗）反而不出这么多报错和卡顿 · 以及优化路径（run13-19 六轮实证 · 2026-11-09）

<!-- meta: tags=专题化,形态演替,内嵌chat,pi agent核心,优化路径 -->

> **TL;DR**：引擎站 4 内嵌 chat 车道五轮+run18-19 共七轮 FAIL 的全部根因归结为一个本质问题——**LLM 和代码之间隔了一层引擎（写盘/测试/回喂），LLM 看不到全貌，每一步都有传达损耗**。L2 pi 窗不出这些错，不是因为 pi 更聪明，而是因为 pi 窗里的 agent **直接操作文件系统**（自己读文件跑测试看报错改代码——所见即所得）。优化路径分三层：层次一已做（红因盒×3+会话持久化 MVP——有效但不够），层次二候拍（A 自愈环升级 pi 精修·B 站4 整体切 pi 窗·C 骨架预投降自由度），层次三结构性最优解=站4 施工岗正式切换为 pi agent 窗形态。

## §一 本质差异（白话一句话）

L2 pi 窗 = **你雇了一个坐在电脑前的程序员**——给他任务，他自己看文件、跑测试、看报错、改代码，一条龙全自己干，错了自己修。

L1 内嵌车道 = **你打电话给一个远程的人**——你念需求给他→他口述代码→你帮他打字→你帮他跑测试→你念报错给他→他口述修改→你帮他改——**每一步都有传达损耗**，而且他看不到屏幕。

**五轮报错和卡顿的全部根因都来自"远程传达损耗"**——不是代码问题，是通信管道问题。

## §二 五轮报错逐个根因（全实证·非猜测）

| 轮 | 报错 | 根因 | pi 窗为什么不出 |
|---|---|---|---|
| run13 | **挂死**（进程 300s 无输出） | 车道写的代码有 `Atomics.wait(10min)` 无 watchdog——引擎没看见（LLM 只吐文本·引擎写盘后跑测试才炸） | pi 窗里 agent **自己跑测试**→自己看到挂→自己修 |
| run14 | **TS2339**（类字段未声明×N） | LLM 输出了不完整的类定义——回喂盒只带截断的错误头尾（400 字），LLM 看不到完整上下文 | pi 窗里 agent **自己跑 tsc**→看到全部错误→自己改 |
| run15 | **TS2322**（SAB 进 transferList） | 同上——回喂截断+变量盒 JSON 包装损耗 | 同上 |
| run16 | **TS2304**（引用未定义名称） | 同上 | 同上 |
| run17 | **路径布局 bug**（.models 直下找 tokenizer.json） | LLM 写的模型加载逻辑路径错——引擎没发现（直到跑考题才炸） | pi 窗里 agent **自己 ls 目录**→发现路径不对→自己修 |

### 五个根因的共同点

**全部来自"LLM 看不到全貌"**——内嵌 chat 模式下，LLM 和代码之间隔了一层引擎（写盘/测试/回喂），LLM 只能通过引擎拼的回喂盒间接看到错误——而回喂盒有截断、有格式转换、有衰减。

pi 窗里 agent 没有这层隔膜——它直接操作文件系统，直接跑命令，直接看输出——**所见即所得**。

## §三 校验不产生错误——校验暴露错误

引擎的校验层（语法门/验收/探针/切片/硬化）是"检查器"——只报告"什么坏了"，不产生错误。

| 校验层 | 它做什么 | 它产生了错误吗 |
|---|---|---|
| 语法门（tsc --noEmit） | 检查代码能不能编译 | ❌ 只报告 TSxxxx 错误·不改代码 |
| 验收命令（vitest run） | 检查行为是否正确 | ❌ 只返回 exit code·不改代码 |
| 探针（第二层） | 验证契约面 | ❌ 只入账 |
| 切片（E2E） | 模拟用户操作 | ❌ 只返回三态 |
| 硬化道（mutation） | 验证考题杀伤力 | ❌ 只判死活 |

**校验不产生错误——校验暴露错误。** 错误来自生成侧（LLM 写的代码）。校验越多=暴露越充分=越好。

**所以问题不在校验——在校验发现错误之后，修复 agent 有没有能力改对。**

## §四 修复 agent 的能力差距（核心问题）

| 能力 | L2 pi 窗里的 agent | L1 内嵌车道的 LLM |
|---|---|---|
| 读完整错误 | ✓ 自己跑测试自己看全量输出 | ❌ 只看回喂盒的 failOut 头尾（headTail 截断） |
| 读完整代码 | ✓ 自己 read 文件 | ❌ 只看 box.previous_attempt 环切 |
| 改代码 | ✓ 自己 write/edit 文件 | ❌ 只能输出全文（引擎写盘） |
| 跑测试 | ✓ 自己 bash 跑命令 | ❌ 引擎跑·LLM 看不到过程 |
| 上下文 | ✓ 会话历史天然持久化 | ❌ 每轮全新 prompt（#501 手拼 MVP） |
| 迭代 | ✓ 同一会话连续精修 | ❌ 每轮全新调用（无记忆） |

**核心差距=工具面**——L2 pi 窗的 agent 有 fs/bash 工具（自己动手）；L1 内嵌车道的 LLM 只能输出文本（靠引擎代劳）。工具差距直接导致修复质量差距——进而导致收敛率差距。

## §五 优化路径三层

### 层次一 · 已落地（红因提示盒×3 + 会话持久化 MVP）

| 治法 | 治了什么 | 效果 | 还剩什么 |
|---|---|---|---|
| #498 挂死盒 | 挂死红因回喂不再空喂 | 只治挂死这一种红 | 类型错/逻辑错不看这个盒 |
| #499 TS2339 盒 | 类字段声明指引 | 只治这一种类型错 | 其他类型错不看 |
| #500 类型族通用三查盒 | 未知类型错给通用三查指引 | 只给方向不给具体修法 | 模型遵从度仍不足 |
| #501 会话持久化 | 回喂从"重组全新消息"变"历史追加" | 消除无状态重抽·红因轨迹持续 | 但 LLM 仍只能看截断的 failOut——看不到完整文件系统 |

**结论**：层次一有效但不够——红因回喂从空喂→有料→但料是截断的+间接的——**距离"agent 自己看全貌自己修"还差工具层**。

### 层次二 · 候拍（三个方案）

| 方案 | 做法 | 效果 | 成本 |
|---|---|---|---|
| **A · 自愈环升级为 pi agent 精修** | 自愈环 ⟲ 时不再调 `chat()`——改为 spawn 一个 pi 会话窗（print·任务=读错误+改代码+跑测试+到绿） | agent 有完整工具（fs/bash）·自己看错误自己修·信息零衰减 | 中（自愈环调用点改 spawn）·每次自愈多一个 pi 壳成本 |
| **B · 站4 施工岗整体切 pi agent 窗**（#504 第一期产品化） | 站4 车道从内嵌 llm.ts → spawn pi 会话窗（= L2 形态正式启用） | 从源头消除回喂损耗——agent 自己写自己测自己修到绿 | 高（编排重构）——但 L2 已实证 332k 全绿 |
| **C · 骨架预投降自由度** | 包侧预投骨架文件（接口空壳+契约注释）·车道填空（不是从零写） | 缩小探索空间→减少类型错/逻辑错 | 需重设计骨架（T1 首跑骨架 throw 导致极速 park 的教训） |

### 层次三 · 结构性最优解（终态建议）

**不是优化内嵌车道——是承认内嵌车道做不了这种高难度任务·把站 4 施工岗正式切换为 pi agent 窗形态（= #504 第一期的产品化落地）。**

| 现状 | 终态 |
|---|---|
| 站 4 车道 = 内嵌 llm.ts chat（无状态重写·回喂盒·语法门/验收由引擎跑） | 站 4 施工 = spawn pi 会话窗（有工具·自验闭环·agent 自己修到绿·窗收口后引擎只跑站 5 判卷确认） |
| 引擎负责：拼盒→调 LLM→写盘→跑测试→读输出→拼回喂→循环 | 引擎只负责：发起窗→窗收口后跑站 5 判卷（exit code 红绿权不变） |
| 校验检查器不产生错误 ✓ | 校验检查器不产生错误 ✓（不变） |
| 修复靠回喂盒（信息衰减→盲改） | 修复靠 agent 自身（有工具·看得到全貌·精修） |

**这就是 L2 形态已经实证的事**——332k 全绿 vs L1 五轮 1.19M 未收敛——不是"pi 更聪明"，是"pi 窗里的 agent 有工具能自己修"。

## §七 概念澄清四则

### 7.1 「盒」是什么

盒（box）=**给 LLM 单次调用的上下文包裹物**——「输出协议的请求面（ADR-0002·指令/数据分离）」。盒族四类：变量盒（正向）/续写盒/单段重发盒/回喂盒。

### 7.2 应用层 reducer ≠ provider 层缓存命中（两层区分）

langchain 的消息归约器管的是「应用层怎么组织 messages」；缓存命中发生在「provider 层前缀字节匹配」。#501 的 buildMessages（追加形态）与 langchain reducer 语义同构——引框架只换 API 糖·不取。待验真点：兼容端点对 cache_control 的支持。

### 7.3 pi agent 的循环范式

pi = **工具调用循环（tool-use loop）**——广义 ReAct 家族·native tool-use API（结构化 tool_use 块）：系统提示+工具定义→LLM 输出→harness 执行→结果回喂→循环。"自然闭环"=写→跑测试→读输出→改在 agent 内部完成。

### 7.4 pi agent 核心七件套

会话容器/系统提示层/工具层/循环器/权限安全层/provider 层/compaction。

## §八 治理环两层关系

| 层 | 位置 | 机制 | 实证 |
|---|---|---|---|
| 夜内自愈环（ticket 级 ⟲） | **班次内**（站4 车道内·不等班结束） | self_heal_retry→park#1→夜末补考→park#2 终局 | run13-16 实转 |
| 班间维修环（M1/M2/M3） | **班次完成后→下一班前**（晨报→诊断→方案候拍→执行） | 三环分权（拍板#84②） | run17 后 M1 病历=归档会话（咬合点） |

## §九 选型律与边界

1. 一次性任务→L2（pi agent 核心）·高频同构+愿投适配→L1（真引擎）·判卷永不 LLM 化（红线）。
2. 止损纪律：预算三路+语法门快速失败+M6 熔断——试错从"失控燃烧"变"可控采样"（单位形态成本降 3 倍）。
3. 边界：本件为讨论沉淀底稿（md）——HTML 成品化候拍；治理票 B 级候追认；L1 后续候业主终裁。
