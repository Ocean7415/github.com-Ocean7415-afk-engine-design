术语白话对照：模板方法模式＝父类定流程（焊死不许改）、子类填内容的面向对象手法｜钩子方法＝基类里留空的「填空题」，每个实例填自己的做法｜spawn 子进程复用＝第二层要跑同一条流水线时不是引用同一段代码，而是另开一个独立进程去跑——隔离性好但代码层是两套｜Pull Up（上提）＝把多处重复的代码上提为一份共享母版的重构手法｜钉版文件＝开工前写「这夜用哪版代码/岗卡/考题」的文件，缺了拒开班。
口述：本册卡3 说「版本化是总闸门」、卡4 说「步④基类化」、卡6 动作七说「拍构成物清单」——这三处共同指向的对象就是骨架，所以值得单独一张卡说清它是什么。把骨架想成全厂唯一一张发动机图纸，图上画三样东西。第一样是流水线的工序顺序（模板方法基类）：夜车开工必须按「入夜门禁六硬项→导入拆单→探针编译装备→施工→质量门→切片验收→报告」的顺序走。这段顺序今天真实存在于代码里（主函数体内），但像一道菜谱整页抄在纸上——第二层要用同一条流水线时，是开一个独立子进程整进程跑（不引用同一段代码），而不是照着菜谱母版各做各的。第二样是标准零件库（机械件包）：五十八个两层共用的零件——记流水账的账本、防偷改考题的判卷守卫三卫、大模型档位旋钮、防提示注入的变量盒封套等；形态上绝大多数是纯函数和常量，只有账本等少数是真类——「零件包」是零件的集合，不是面向对象的类库。第三样是交货单格式（交接契约）：班与班之间交货凭机器可查的凭据，凭据格式已在码里，「接口契约台」（逐项对账的机器面）还挂在候拍窗 W-152 名下。
所以直答：骨架现在不是一个实体对象类——三件里没有一件以「类」为中心形态存在。基类化拍板之后才是：把焊死的站序上提为抽象基类的模板方法，各站留填空钩子，第一层填「造客人 APP 的做法」、第二层填「管团队的做法」——届时的样子见下方伪代码示意。为什么本册把它当总闸门的对象？三个理由：一是卡5 差距一（两层同构靠文档不靠代码）的治本方就是基类化——同构从「文档互指」变「继承关系」，改一处两处自动跟；二是版本记账需要它——「骨架版本 S1.x」要先成为边界清晰的实体，才钉得进动作八的钉版文件三键里；三是自举需要它——造新版的车和被造的零件共享同一张图纸，自举核账的账才对得上。排序上它是 P2「提效不设卡」：进程边界已提供隔离复用，基类化是省力活不是保命活。
// 步④基类化后的形态示意（非实码·真实设计以步④拍板件为准）
abstract class NightShiftSkeleton {        // ← 骨架 S1.x 的实体形态
  final async run(pkg): ExitCode {         // 模板方法：站序焊死，子类不许改流程
    await this.preflight();                // 段0 入夜门禁
    const plan = this.importAndSplit(pkg); // 段1 导入+拆单
    await this.build(plan);                // 段2 施工
    await this.verify();                   // 段3 验收
    return this.report();                  // 收尾报告
  }
  protected abstract preflight(): void;    // 站实现＝填空（钩子方法）
  protected abstract build(plan): void;
}
